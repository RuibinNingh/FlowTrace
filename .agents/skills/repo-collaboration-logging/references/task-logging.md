# 维护任务日志

## 用任务记录支持恢复与核验

任务日志回答“为什么改、实际改变了什么、验证证据在哪里”。它与模块文档、计划进度配合：模块文档描述当前系统，进度描述整件事的位置，任务日志保存本次事实。不要把三者写成重复流水账。

仓库内有持久化改动时，按目标项目规则留下任务证据；只读调查或仅在仓库外生成用户要求的交付包，不为留痕制造源仓库空改动。无需复制 OMRS 的真实日志来建立新项目的历史。

## 任务身份与生命周期

OMRS 的命名示例是 `YYYY-MM-DD_topic.md`，主题由小写英文、数字和连字符组成。日期必须有效，标题日期与文件名一致，任务标识与主题一致；新任务使用新主题，冲突时加 `-2` 等后缀。

任务块放在文件开头，便于读取状态与生成索引：

```markdown
> **任务**
> - 标识：example-task
> - 状态：进行中
```

采用两种状态就能覆盖常见接力：

| 基线中的状态 | 允许的变化 |
|---|---|
| 新建任务 | 新建日志，填写事实；尚未完成时为进行中 |
| 进行中 | 同一任务跨轮续写同一文件；交付时标为已交付 |
| 已交付或无状态块的旧日志 | 保留原文，只追加带实际日期的勘误；不覆盖、删除或改名 |

交付后的新工作建立新日志。无状态块的旧任务需要续作时，也新建有状态记录并说明关联。历史勘误不能代替本次任务日志，不能把后续工作伪装成旧日期的原始事实。

勘误使用 `## 勘误（YYYY-MM-DD）`，写清原结论、修正结论与依据，并在当前任务日志说明这次勘误。历史保护针对可追溯性，不禁止对已知错误作明确更正。

## 五节内容避免只写“已完成”

完整结构见[任务日志模板](../assets/templates/task-log.md)。五节均填写具体内容；确实没有的项目写“无”并说明必要边界。

| 章节 | 最少需要的事实 |
|---|---|
| 背景 | 用户原话、基线、执行环境、关联计划与目标 |
| 行为变化 | 用户或调用方实际受到的影响；纯整理也说明 |
| 影响文件 | 根据实际差异列出本任务文件与原因 |
| 已执行验证 | 真正运行的命令、结果、证据位置；保留失败及重跑 |
| 未执行验证 | 尚未运行的检查及原因；区分环境缺失与范围外事项 |

补丁交接可另加“合入”节：补丁基线、应用命令、接收方命令、预期结果及验收标准。预期结果不能混进已执行验证。计划任务的下一步同时登记到进度文件，避免只有发送者知道如何继续。

“已交付”表示本次约定的交付物已完成，不自动表示已部署、已推送或所有环境都已验证。不同状态应分别写清。

## 门禁保护结构与生命周期

迁移时先复用项目已有检查器；需要新建时，按实际规模选择以下能力。此包没有附带 OMRS 的检查脚本，采用模板不会自动获得这些门禁。

1. **结构检查。** 验证文件名、日期、任务块、状态、必填章节及非空内容；模块文档检查速查头和内部引用。
2. **变更覆盖。** 从选定基线收集真实差异，逐份核对映射中的必更文档，以及本次新增或续作中的任务日志。仅修改历史不能冒充本次留痕。
3. **历史保护。** 已交付及旧日志与基线逐字比较，只允许保留原文后追加规范勘误；删除、改名和覆盖也需识别。默认不追溯强制改造全部历史格式。
4. **派生索引。** 从允许纳入的文件生成索引，忽略私人或被排除文件。生成器输出应可重复，不能将不存在的文件写入索引。
5. **事实核对。** 将日志中的验证结论与命令输出、浏览器证据及实际代码对应。形式检查无法证明“通过”确实发生过。

如果实现这类门禁，用临时小仓库验证新增、进行中续写、交付、历史追加、历史覆盖、删除和改名等真实场景，同时确认合法变化不被误报。不要只测试正则能匹配模板。

## 收尾顺序

先完成本次授权的功能或交付物，再复核差异，同步受影响文档，补齐真实任务证据和计划进度，生成必要索引，运行风险相称的检查。检查失败就保留失败事实并修正；能力缺失则明确未执行及下一步，不把文档合格等同于业务验收完成。
